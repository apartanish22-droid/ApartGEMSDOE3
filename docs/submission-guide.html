Required file contract

Follow the current official DrivenData problem page ↗ and upload portal if any instruction differs. The page specifies a predicted single-band GeoTIFF on the training grid.

  • One raster band, `float32` predictions, with valid predicted values in [0, 1].
  • Exact training-grid CRS, shape, pixel size, bounds, and geotransform; a visually similar raster or reprojection is not sufficient.
  • No NaN/NoData inside the prediction footprint. Preserve the official null/NaN outside-footprint convention; confirm the exact mask using the authorized sample/grid before validation.
  • No NaN or infinity inside the footprint; do not silently clip, normalize, or overwrite failed predictions just to pass a portal check.
  • Save as one `.tif` and use only an archive format if the current portal explicitly permits it. Do not add auxiliary bands or unrelated files.

The official task page supplies `EPSG:32611` and a 100 m training grid. Treat those as expectations to verify against an authenticated sample raster, not values to hard-code. The official download page was login-gated in this review. The repo contains owner-mirrored sample/known-fault rasters and derived GeoDAWN inputs, but they are not an authenticated organizer download; verify provenance and hashes before use.

Step-by-step submission workflow

  1. Check the home-page status and the single run card. Proceed only after a separate selector authorizes a candidate. The card must say `promote`, not `negative`; the current card is `negative`. A public leaderboard value or reported peer score cannot satisfy this gate.
  2. Acquire and provenance-check inputs. Sign in directly to DrivenData in your own browser for official downloads; this review saw the data page redirect to login. Existing owner-mirrored sample/known-fault rasters and GeoDAWN derivatives are present in the repo, but are not a substitute for an authenticated full training-feature download. Verify the source manifest, hashes and grid. Never paste credentials into chat or Git.
  3. Reproduce the pinned pipeline. Use the repo's existing auditable feature/evaluator/writer code and the shared template's cache/evaluator/writer where the active lane requires it. The full official feature stack and assigned method paragraph are still absent; do not invent a lane or create a private metric fork. If shared-tool policy is wrong, resolve it in the shared template and record its pinned revision.
  4. Pass leakage and holdout tests before export. Build fold-specific catalogue features from visible faults only; hide complete fault segments with the required buffer; mask visible fault pixels exactly; test each feature alone. Investigate any AUC above 0.90 as a leakage canary. Report pooled HOLDOUT-DTI with evaluator version, withheld-positive count, and 95% CI.
  5. Pass uniqueness before placement and again on final dots. Compare the candidate surface to the complete registry. Stop/log if absolute Spearman rank correlation is above 0.90 or if more than 70% of final dots fall within 3 pixels of any registered raster. Check the up-to-date registry; the focus-nine comparison alone is not enough.
  6. Run the automatic validator after policy reconciliation. The current exact-file review reports the MRCJ research TIFF passes the core one-band/float32/grid and in-footprint range checks, but fails official null/NaN-outside compliance because the exterior is zero with no nodata tag. The pinned shared `57GEMSDOE` validator also enforces whole-array finite values and zero outside, so resolve the mismatch against the authenticated sample/organizer guidance in the shared template; do not maintain a private validator fork or advertise a format-only pass as submit-ready. Save the complete validator output and SHA-256 in the canonical run card.
  7. Create a unique artifact name and concise note. Use a fresh method/lane tag, UTC timestamp and a hash-derived suffix. Keep the portal note at or under 140 characters. Never reuse an old filename for changed bytes.
  8. Prepare an accurate AI-use disclosure and final documentation. The DOE Rules allow generative AI but require the submission narrative to state whether and how it was used. This project used an AI agent for repository review, research synthesis, website/documentation and test scaffolding; accurately disclose any use of this work and any later model/data analysis. Finalists may also need complete code assets and reproducibility documentation. Do not claim work or verification that was not performed.
  9. Review account eligibility and the single-final-submission rule. The official rules state a maximum of three feedback submissions per week, but by the deadline a competitor must select only one final submission for evaluation across both prize rounds. Verify the current portal limits and your own eligibility/attestations; this repository cannot do that for you.
  10. Only after separate selector approval, upload through DrivenData. Open the official competition page, use its current submission/upload control, choose the exact validated `.tif`, review the displayed filename and any portal validation result, and submit. Save the organizer confirmation/receipt with its score and submission identifier. This page does not select a weekly slot or authorize an upload.
